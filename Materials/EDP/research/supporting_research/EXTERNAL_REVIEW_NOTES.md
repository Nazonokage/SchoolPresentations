## Corrections and decisions for subsequent authoring

1. Preserve one module per teaching day. The latest report suggests merging topics to resolve the calendar gap, but that does not authorize combining two scheduled modules in one meeting. Shorter exercises also do not create additional teaching days.
2. Do not compress all conditionals, loops, and functions into one overloaded refresher. Prefer four clear opening units: variables/types/operators; conditionals; loops; functions/parameters/returns. Follow with arrays/objects and an explicit TypeScript bridge. Rebalance later topic coverage within the 23-module inventory rather than silently increasing the count. This is an authoring recommendation, not a finalized timetable.
3. The latest EDP sequence refers to typed promises without an explicit TypeScript introduction. Add that bridge before relying on TypeScript syntax; do not assume ADET attendance substitutes for teaching it in EDP.
4. The early ADET study-timer example presupposes timing and lifecycle knowledge. Use a counter or budget interaction first; schedule timers after their prerequisites.
5. Keep summative exams separate from numbered teaching modules. Include the Finals summative before the final periodical practical exam.
6. Use the supplied institutional calendar and the existing calculated capacity scenarios, not the report's rough 18–20-day estimate. The actual weekdays and College Week arrangements remain unknown.
7. The CHED claim is supported in the report only by secondary summaries, not a directly inspected official order. Do not claim official compliance, required outcomes, or binding revisions on that basis. An official CHED document must be verified before a formal mapping is added.
8. Approximate SDK numbers, update dates, and vague licensing statements are not a reproducible technical baseline. Freeze and test actual package versions when producing executable lessons. Record licenses only from an explicit source.
9. No verified direct PDF/DOCX download has been added by this report. HTML documentation is still useful; do not describe these reports as a collected downloadable textbook library.
10. Use a manageable solo project scope based on demonstrated outcomes, not the report's requirement to use a majority of all core modules. A focused, reliable app is a better assessment than a checklist of unrelated features.
