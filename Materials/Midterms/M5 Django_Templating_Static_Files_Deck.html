00_intro.py

Where We Are, and Where We're Going

So far, every view has returned plain text with HttpResponse. That doesn't scale to a real webpage.

😩 The Problem

  • HTML strings glued together inside Python — ugly and unmaintainable
  • Every page repeats the same header, nav, and footer
  • CSS and images have no clean, official "place to live"
  • Designers and backend devs keep stepping on each other's code

✅ What Fixes It

  • Templates — real .html files, with just enough logic to stay dynamic
  • Template inheritance — write the layout once, reuse it everywhere
  • Static files — a dedicated, versioned home for CSS, JS, and images
  • Together: Python handles logic, templates handle presentation

The Problem, in Actual Code

Same page, two ways. One of these does not scale past a single page.

😩 the bad way

          

          

            
✅ the django way

            

          

        

        

          
What actually changed

          
The HTML moved out of the Python file and into its own .html file. The view's only job now is to gather data and hand it to render() — no string-building, no escaping headaches, no repeated layout on every single view.

        

      

    


    
    

      

        
02_template_folder.py

        
Where Templates Live

        
Convention over configuration: Django already knows where to look.

        

          

myapp/

  templates/

    blog/ ← namespaced by app name

      layout.html

      post_list.html

  views.py

  models.py

  urls.py
          

          

            
Why the extra blog/ folder?

            
    
              
  • Two apps can both have a list.html without colliding
    • 
              
  • Django's loader searches every app's templates/ folder — namespacing keeps things sane
    • 
              
  • render(request, "blog/post_list.html", context) is how a view points at one
    • 
            

            
Rule of thumb: template path = appname/templates/appname/file.html.

          

        

      

    


    
    

      

        
03_template_syntax.py

        
Template Syntax — The Four You Need

        

          

            
{{ variable }}

            
Prints a Python value straight into the HTML. Nothing fancy — just output.

          

          

            
{% if condition %}

            
Runs a conditional check — show this block only if it's true, closed with {% endif %}.

          

          

            
{% for item in list %}

            
Loops over a list from the view's context, closed with {% endfor %}.

          

          

            
{% block name %}

            
Marks a section a child template is allowed to override. The foundation of inheritance.

          

        

        

          
Quick logic

          
{{ }} = "print this." {% %} = "do this" (a tag/logic block). That's the entire mental model.

Template Inheritance — Write the Layout Once

        

          
        

        

          
The deal

          
The parent defines the skeleton (nav, footer, {% block content %}). Every child {% extends %} it and only fills in the block — the nav and footer never get retyped.

06_setup_guide_part2.py

        
Setup Guide, Part 2 — Templates & Static Config

        
Four quick checks. Skip these and your templates or CSS silently fail to load.

        

          

            
terminal + settings.py

            

          

          

            
Step 1 Create the namespaced folders first: mkdir -p for both templates/<app>/ and static/<app>/.

            
Step 2 Confirm APP_DIRS: True in settings.py — it's what makes Django auto-scan every app's templates/ folder. startproject sets this by default, but it's worth checking.

            
Step 3 Confirm 'django.contrib.staticfiles' is listed in INSTALLED_APPS — this is what powers {% load static %}.

            
Step 4 Set STATIC_URL and (optionally) STATICFILES_DIRS for any extra shared static folders outside individual apps.

            
Done Once these four are in place, the code on the next few slides will work exactly as shown.

Code Breakdown — views.py + Templates

        

          

            
python + django template

09_static_files.py

        
Static Files — CSS, JS & Images

        
"Static" = files Django serves as-is, without running any Python on them.

        

          

myapp/

  static/

    blog/ ← namespaced, same idea as templates

      style.css

      script.js

      logo.png

  templates/blog/...
          

          

            
Why not just hardcode the path?

            
    
              
  • Django can move, version, or serve static files from a CDN in production
    • 
              
  • {% static %} always builds the *correct* URL, wherever files actually live
    • 
              
  • A hardcoded /static/style.css silently breaks the moment that changes
    • 
            

          

        

      

    


    
    

      

        
10_static_code.py

        
Code Breakdown — Loading Static Files

        

          

            
django template + settings.py

            

          

          

            
{% load static %} Must appear before any {% static %} call — it "unlocks" the tag for this template.

            
{% static 'blog/style.css' %} Resolves to the correct URL — never type /static/... by hand.

            
STATIC_URL The URL prefix Django serves static files under, e.g. /static/.

            
STATICFILES_DIRS Extra folders Django should also search, beyond each app's own static/ folder.

13_why_we_do_this.py

        
Why We Bother With Any of This

        

          
Separation of concerns
Python handles logic and data. Templates handle presentation. Mixing the two turns into spaghetti fast.

          
DRY (Don't Repeat Yourself)
Inheritance means your nav and footer exist in exactly one file, not copy-pasted across twenty pages.

          
It scales with a team
A designer can edit style.css and templates without ever touching your Python logic, and vice versa.

        

        

          
The bigger picture

          
This is also exactly why frameworks like React exist — same problem (separating structure from logic), different tool. Learn the *reasoning* here, and it transfers everywhere.

recap.py

        
Recap Before You Go

        
The essentials worth remembering.

        

          
✓{{ variable }} prints a value. {% tag %} runs logic.

          
✓Templates live in appname/templates/appname/ — namespaced to avoid collisions.

          
✓A child template's {% extends %} must be the very first line.

          
✓Context dict keys in render() must match variable names used in the template.

          
✓Static files live in appname/static/appname/ — same namespacing idea as templates.

          
✓{% load static %} comes first; {% static 'path' %} builds the real URL.

Answer Key

        

          

            
Multiple Choice

            
1. B — {{ variable }} is output; {% %} is logic.

            
2. B — {% extends %} inherits a parent layout.

            
3. B — blog/templates/blog/ is the namespaced convention.

            
4. A — {% load static %} unlocks the {% static %} tag.

            
5. B — STATICFILES_DIRS adds extra search folders.

          

          

            
Identification

            
1. {% for %} — loops over a list from the context.

            
2. {% if %} — conditionally renders a block.

            
3. templates — Django's default template folder name.

            
4. {% block %} — a replaceable section for child templates.

            
5. {% static %} — builds the correct static file URL.
