Closing the Loop

You've built models, forms, and sessions. Three things left before this feels like a real, shippable project.

1. Name the pattern

Every form view you've written already follows one shape. Naming it makes it something you can apply on autopilot.

2. Stop hardcoding

Hardcoded URLs and repeated logic are the #1 reason small Django projects become fragile fast.

3. Ship it

A project that only runs on your machine isn't finished. Docker is how it runs the same way everywhere.

04_best_practices.py

        
Best Practices — Five Habits Worth Keeping

        

          
reverse()
Build URLs from their name, never hardcode the path string.

          
app_name
Namespace an app's URLs so two apps can both have a route called "list".

          
Inheritance
Write the layout once with {% extends %} — never copy-paste nav and footer.

          
Session init check
Always .get(key, default) — never assume a session key already exists.

          
csrf_token
Every single method="post" form, no exceptions, ever.

        

      

    


    
    

      

        
05_best_practices_code.py

        
Code Breakdown — app_name + reverse() Together

        

          

            
python + template

            

          

          

            
app_name = "tasks" Declared once in the app's urls.py — now every route name needs the tasks: prefix elsewhere.

            
reverse("tasks:task_list") Used in Python code (views, redirects) — resolves to the real path at request time.

            
{% url 'tasks:add_task' %} The template-side equivalent — same idea, different syntax.

            
Why the prefix If another app also names a route "list", tasks:list and blog:list stay unambiguous.

          

        

      

    


    
    

      

        
06_sample_project.py

        
Sample Project: Refactoring the Tasks App

        
Take the tasks app from the last lecture and apply all four best practices in a single pass. Full code, file by file, next.

        

          
1
Add app_name = "tasks" to tasks/urls.py — every route name now needs the tasks: prefix.

          
2
Replace every hardcoded redirect("/tasks/...") in views.py with redirect(reverse("tasks:...")).

          
3
Replace every hardcoded <a href="/tasks/..."> in templates with {% url 'tasks:...' %}.

          
4
Result: renaming any route in urls.py is now the only change ever needed — nothing else to hunt down.

Why We Bother With Any of This

Docker — "It Works on My Machine," Solved

        
Time to containerize the feedback app you just built, so it runs identically anywhere.

        

          

            
😩 Without it

            
    
              
  • Your Python version, OS, and installed packages differ from your teammate's
    • 
              
  • "Works on my laptop" is not the same as "works on the server"
    • 
              
  • Setting up a new dev's machine takes half a day of troubleshooting
    • 
            

          

          

            
✅ With it

            
    
              
  • A container packages your code, Python version, and dependencies together
    • 
              
  • The exact same container runs identically on your laptop, a teammate's, or a real server
    • 
              
  • New developer? docker-compose up and they're running the whole project in minutes
    •

13_dockerfile_code.py

        
Code Breakdown — The Dockerfile

        

          

            
dockerfile

            

          

          

            
FROM python:3.12-slim The starting image — a minimal Linux with Python already installed.

            
WORKDIR /app Every command after this runs inside /app — the container's version of your project folder.

            
COPY requirements.txt . first A deliberate order — Docker caches this layer, so dependencies aren't reinstalled every time your code changes.

            
CMD [...] The command that runs the moment the container starts.

          

        

      

    


    
    

      

        
14_compose_code.py

        
Code Breakdown — docker-compose.yml

        

          

            
yaml

            

          

          

            
services: Each key is one container. This project needs two — the app, and its database.

            
web Builds from the Dockerfile right next to it, and maps the container's port 8000 to your machine's.

15_docker_commands.py

        
The Commands You'll Actually Use

        

          
docker-compose up --build
Builds the images (first time, or after a Dockerfile change) and starts everything.

          
docker-compose up -d
Starts everything in the background — your terminal stays free.

          
docker-compose exec web python manage.py migrate
Runs a management command inside the running web container.

          
docker-compose logs -f web
Tails the app's live output — your main debugging window.

          
docker-compose down
Stops and removes the containers — a clean slate for next time.

17_why_docker.py

        
Why We Bother Containerizing

        

          
Consistency
The exact same environment runs on every machine — no more "it worked yesterday" mysteries.

          
Fast onboarding
A new teammate is running the full project — app and database — with one command.

          
A real deployment story
The container that runs on your laptop is the same one a production server runs — no surprises at launch.

        

        

          
The bigger picture

          
This is the same foundation behind shipping APIs, adding authentication, or calling external services later — a containerized app is what makes all of that reliable to build on top of.

recap.py

        
Recap Before You Go

        
The essentials worth remembering.

        

          
✓Every form view is the same shape: GET displays, POST validates, valid saves + redirects, invalid re-renders with errors.

          
✓Never hardcode a URL path — use reverse() in Python and {% url %} in templates.

          
✓app_name namespaces an app's routes so two apps can safely reuse the same URL name.

          
✓A Dockerfile builds one image; docker-compose.yml runs multiple containers together.

          
✓docker-compose exec web ... is how you run management commands inside a running container.

          
✓Containerizing isn't optional polish — it's what makes "works on my machine" stop being a problem.
