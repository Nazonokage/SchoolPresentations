01_http_cycle.py

The Request → Response Cycle

Every single page load is this loop, over and over.

Stateless

Each request stands alone — the server keeps no memory of the last one unless sessions/cookies say otherwise.

Client-initiated

The browser always starts it. The server only ever replies, never pushes uninvited.

Every reply has a code

A response is never just HTML — it always ships with a 3-digit status code first.

02_get_vs_post.py

GET vs POST — Same Door, Different Manners

GET Reads

  • Retrieves data — never changes server state
  • Parameters ride in the URL (?q=django)
  • Safe to refresh, cache, and bookmark
  • Used for: viewing pages, search results, links

POST Writes

  • Submits data that changes something server-side
  • Data travels in the request body, not the URL
  • Browsers warn before resubmitting
  • Used for: registration, login, checkout, edits

03_status_codes.py

        
Status Codes at a Glance

        
Every code is a 3-digit sentence. The first digit tells you the genre.

        

          

            
2xx — Success

            

              200 OK
              201 Created
              204 No Content
            

          

          

            
3xx — Redirection

            

              301 Moved
              302 Found
              304 Not Modified
            

          

          

            
4xx — Client Error

            

              400 Bad Request
              403 Forbidden
              404 Not Found
            

          

          

            
5xx — Server Error

            

              500 Internal Error
              502 Bad Gateway
              503 Unavailable
            

          

        

        

          
Quick logic

          
2xx = "got it." 3xx = "look over there." 4xx = "you messed up." 5xx = "I messed up." Read the first digit before you panic about the rest.

Django's MVT, Not MVC

        
The #1 trap in every quiz: Django's "View" does the Controller's job.

        

          
        

        

          
Model
Data & DB logic. Same name, same job as MVC.

          
View (views.py)
Decides the logic — this is MVC's Controller wearing a different name tag.

          
Template
The actual HTML — this is what MVC calls its "View."

        

      

    


    
    

      

        
05_routing.py

        
How to Code a Route — urls.py + views.py

        

          

            
python

            

          

          

            
path() Maps one URL pattern to one view function — the receptionist's directory.

            
<str:name> Captures any text and hands it to the view as name.

            
<int:year> Two converters in one path work fine — Django just fills both parameters, in order.

            
<slug:tag> Built for URL-safe words: letters, numbers, hyphens, underscores — perfect for blog tags.

            
<uuid:id> Matches a formatted UUID — common for public IDs that shouldn't be guessable like 1, 2, 3.

            
name= Lets templates reference this URL by name, so it survives if the path text ever changes.

            
Golden rule Whatever's inside <type:name> must match the view's parameter name — exactly.

          

        

      

    


    
    

      

        
06_fstrings.py

        
F-Strings — How They Actually Work

        

          

            
python

            

          

          

            
f" " The f prefix turns on { } substitution inside the string.

            
{name} Anything inside the braces is plain Python — it runs, then gets dropped into the string.

            
{name.capitalize()} You can call a method right inside the braces — no separate variable needed.

            
{a + b} Even arithmetic works inside the braces — Python evaluates it first.

            
Nested calls A function that returns an f-string is one of the most common patterns in Django views.

recap.py

        
Recap Before You Go

        
The essentials worth remembering walking into the actual exam.

        

          
✓GET reads, POST writes — GET params live in the URL, POST params live in the body.

          
✓Status codes read by their first digit: 2xx ok, 3xx redirect, 4xx your fault, 5xx server's fault.

          
✓Django is MVT, not MVC — views.py is the Controller, template.html is MVC's "View."

          
✓Path converter names in urls.py must match the view function's parameter names exactly.

          
✓An f" " string runs whatever's inside { } first — method calls and math both work.

          
✓.capitalize(), .title(), and [::-1] read left to right, one method at a time.

          
✓migrate only builds tables — it never creates the database itself.

          
✓Since Django 5.0, logging out requires a POST request, not a plain link.

POST or GET?

            
1. GET — plain links always fetch, never submit.

            
2. POST — the form explicitly sets method="post".

            
3. GET — typed URLs are always retrieved with GET.

            
4. POST — it changes state (charges money), so never GET.

            
5. GET — the decorator itself restricts it to GET.

          

          

            
Identify the Status Code

            
1. 200 OK — standard success response.

            
2. 201 Created — a new resource now exists.

            
3. 404 Not Found — the resource isn't there.

            
4. 403 Forbidden — recognized, but not allowed in.

            
5. 500 Internal Server Error — the server itself broke.
