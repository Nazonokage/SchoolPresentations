The Problem · Before Path Converters

One Name, One Route, One Function

  • To say hello to Brian and David, you'd write a separate view for each, and a separate path for each.
  • Now add Harry, Ron, Hermione — and every new name means another function and another route.
  • That's not a web app, that's a wall of copy-pasted code that grows forever.
urls.py — the tedious way
path("hello/brian/", views.brian) path("hello/david/", views.david) path("hello/harry/", views.harry) # ...and it never ends
📇
Real-life analogy
It's like printing a separate business card for every single visitor by name instead of one template that just fills in whoever walks through the door.
Step 1 · The Fix

Path Converters: Placeholders in the URL

  • Django lets you write a route with a placeholder instead of a literal string, using angle brackets: <str:name>.
  • str is the converter type — it tells Django "match any string here."
  • name is the variable name — whatever gets matched is captured and handed to your view under that name.
  • One route now matches /hello/brian, /hello/harry, /hello/hermione — literally any string after /hello/.
urls.py
path("hello/<str:name>", views.greet, name="greet")
🎫
Real-life analogy
Like a raffle ticket template with a blank line for "NAME" — one printed design handles every attendee, because the blank gets filled in per person instead of reprinting the whole ticket.
Step 2 · Read The Code · Part 1

The View Now Accepts a Parameter

Whatever the path converter captures gets passed straight into your view function as an argument.

views.pyOne function replaces every per-name function
def greet(request, name):
    return HttpResponse(f"Hello, {name}!")
urls.pyThe captured value's name must match the view's parameter name
from django.urls import path
from . import views

urlpatterns = [
    path("", views.index, name="index"),
    path("<str:name>", views.greet, name="greet"),
]
📦
Real-life analogy
The URL is a delivery box labeled name. The view function is the person unpacking it — it just needs a parameter with the matching label to receive what's inside.
Step 3 · Python Refresher

Formatted Strings: Plugging Variables Into Text

  • The f before a string turns it into an f-string — Python substitutes anything inside { } with its actual value.
  • This isn't Django-specific — it's plain Python, which is exactly why Django can hand you the request and just let you write normal code.
  • Without the f, Python would print the literal text "Hello, {name}!" — braces and all.
PYTHON SHELL
>>> name = "harry" >>> f"Hello, {name}!" 'Hello, harry!'
Step 4 · Beyond Just Substitution

Any Python Logic Can Run on the Way Out

views.py
def greet(request, name): return HttpResponse(f"Hello, {name.capitalize()}!")
  • Every Python string has built-in methods — .capitalize() is just one of them.
  • If it's valid Python, Django will happily run it before the response goes out — there's no special "Django way" to transform data.
  • So /hello/hermione now renders "Hello, Hermione!" with a capital H, automatically.
🎛️
Real-life analogy
The URL hands the view raw ingredients; Python is the kitchen. Nothing stops the view from cooking that ingredient — capitalizing, trimming, reversing — before plating the response.
Sample Use Case

Building a Parameterized Profile Route

ScenarioA mini "user profile" page, one route for every user
Imagine a site where /profile/<str:username> should work for any registered username, without writing a new view per user — exactly the pattern real sites like Twitter/X use for twitter.com/<username>.
# urls.py
path("profile/<str:username>", views.profile, name="profile")

# views.py
def profile(request, username):
    return HttpResponse(f"Welcome to {username.capitalize()}'s profile!")
Why this matters
One route, one view, and infinite valid usernames — this is the exact mechanism that lets large-scale sites avoid writing millions of individual routes.

Answer Key · Part 1 · Multiple Choice

Multiple Choice — Answers

1. B — path("hello/<str:name>")
Angle brackets are Django's path-converter syntax. A is a literal (non-dynamic) path, C is template-string syntax from another framework, and D isn't valid Django syntax at all.
2. C — The URL path converter
Django calls the view with whatever the path converter captured, passed in as an argument whose name must match. It isn't a global, a settings value, or a hardcoded default.
3. C — Enables substitution inside {}
The f prefix makes Python evaluate whatever is inside { } and insert the result. It works on any expression, not just numbers or file paths, and it doesn't force any case change on its own.
4. B — .capitalize()
.capitalize() upper-cases only the first letter and lower-cases the rest. .upper() would capitalize every letter, and .title_case() / .first() aren't real string methods.
5. C — Scales to infinite inputs
One parameterized route replaces an ever-growing wall of hardcoded ones — the whole point of the lesson. Django doesn't force this pattern, it isn't primarily about speed, and views.py is still required either way.
Answer Key · Part 2 · Identification

Identification — Answers

6. Path converter syntax — <type:name> (e.g. <str:name>)
The angle brackets tell Django "this segment is dynamic"; the part before the colon is the converter type, the part after is the variable name.
7. Parameter-name matching
Whatever name is used inside <str:name> in urls.py must be spelled identically as the view function's parameter — Django passes the captured value by that name.
8. The f prefix (f-strings)
Placing f before a string literal turns on { } substitution, letting Python variables be embedded directly in the text.
9. .capitalize()
A built-in Python string method that upper-cases the first character and lower-cases the rest — used here to make captured names look presentable.
10. Twitter/X profile URLs — twitter.com/<username>
The lecture's real-world example of one dynamic route serving infinite valid values, exactly like the /profile/<str:username> pattern built in this deck.
