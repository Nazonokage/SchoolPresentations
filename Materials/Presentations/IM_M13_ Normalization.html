Main lesson · 1

What is database normalization?

Normalization is the process of organizing data in a database to minimize data redundancy and improve data integrity. It divides larger tables into smaller, more manageable tables and establishes relationships between them.

It ensures data is stored consistently and logically, makes queries and updates easier and less error-prone, and can improve performance by reducing the amount of data processed.

Main lesson · 2

The normal forms

Normalization is done in steps called normal forms. Each builds on the previous one and adds constraints.

Normal formRequirement and description
1NFAtomic values and a primary key. All tables must have a primary key, and all attributes must be atomic (a single value, not lists or arrays).
2NFNo partial dependencies. Must be in 1NF, and all non-key attributes must depend on the entire primary key (relevant for composite keys).
3NFNo transitive dependencies. Must be in 2NF, and no non-key attribute should depend on another non-key attribute.
BCNFSuperkey dependency. A stricter version of 3NF: every determinant must be a candidate key.
4NF and 5NFMultivalued and join dependencies. Highly specialized forms for complex relational structures; rarely used in standard application development.
6NFIrreducible relations. Decomposes tables to the minimum level of relations with zero redundancy.

Important: not all databases need the highest normal form. The level depends on the use case, performance requirements and architecture.

Third Normal Form (3NF)

If the Orders table had a Customer Address column, that would be a transitive dependency (Order ID → Customer ID → Customer Address). Splitting the tables in Step 2 eliminated the redundancy, so the tables are now in 3NF.

Modern update

Denormalization and NoSQL

Normalization (3NF/BCNF) is the gold standard for OLTP systems like banking, where accuracy is paramount. Modern architecture adds trade-offs.

Denormalization for analytics (OLAP)

In data warehouses, query speed matters more than strict integrity. Star and Snowflake schemas (highly denormalized) avoid expensive JOINs.

JSON in relational databases

PostgreSQL with JSONB stores semi-structured, unnormalized data in one column, blending relational integrity with NoSQL flexibility.

NoSQL and document databases

MongoDB and DynamoDB explicitly avoid normalization. Related data nests in one JSON-like document, e.g., an Order with customer info, product details and quantity. Reads are very fast, at the cost of potential duplication.

Pro tip: normalization is a spectrum. Normalize core financial transactions to 3NF; consider denormalization or a document model for a product catalog or user profiles.

Analogy

The inventory

Unnormalized

A giant spreadsheet where every row holds a customer’s whole history, address and products. If a customer moves, you change their address in 50 rows and risk typos (data anomaly).

Normalized (3NF)

Separate folders for Customers, Products and Orders. Orders just say “See Customer folder #123”. If the customer moves, update one place.

Denormalized (modern analytics)

A printed report listing every order with the full address and product name. Redundant, but fast for a manager to read without flipping between folders.

Real-world use case

Checkout vs. recommendation engine

Checkout system (OLTP)

A highly normalized relational database (3NF). When you buy a product, the price must be accurate, inventory decremented exactly once, and the transaction ACID-compliant.

Recommendation engine (OLAP)

A data warehouse or NoSQL system with massive, flattened, denormalized data (“User X bought Product Y”). Redundancy doesn’t matter: the goal is fast analytical queries over billions of records.

FAQs

Common questions

1NF vs. 2NF?

1NF: atomic values and a primary key. 2NF: 1NF plus every non-key column depends on the entire primary key (no partial dependencies).

3NF vs. BCNF?

3NF removes transitive dependencies. BCNF is stricter: every determinant must be a candidate key. It handles edge cases with overlapping candidate keys.

When to stop normalizing?

Up to 3NF or BCNF is usually enough for OLTP. 4NF to 6NF often creates too many tables and degrades performance because queries need too many JOINs.

Does it apply to NoSQL?

Not strictly. NoSQL uses an embedded data model (related data in one document), an intentional form of denormalization.

Key quotes

Key definitions to remember

Normalization

Organizing data to minimize redundancy and improve integrity.

Partial dependency

A non-key attribute depends on only part of a composite primary key (removed in 2NF).

Transitive dependency

A non-key attribute depends on another non-key attribute (removed in 3NF).

Denormalization

Deliberate redundancy to speed up reads, common in analytics and NoSQL.

Recap

Normalize for integrity, denormalize for speed

Normalization structures a relational database to reduce redundancy and improve integrity, progressing from 1NF to BCNF.

Strict normalization (usually up to 3NF) is crucial for transactional systems, while modern architectures often use denormalization or NoSQL document models to optimize read performance and scale for analytical or flexible workloads.
