Main lesson · 1

What is SQL optimization?

SQL optimization improves database performance by reducing the resources (CPU, memory, I/O) a query needs.

Faster execution

Queries return results sooner.

Lower cost

Lower cloud infrastructure costs.

Better scalability

The application keeps up as data grows.

Main lesson · 3

Metrics for analyzing query performance

To optimize a query, you must measure it.

Execution time

Total time from submission to results.

I/O operations

Disk reads and writes. High I/O usually means a full table scan (no index used).

CPU and memory usage

High usage may indicate complex sorting, massive JOINs or missing indexes.

Wait time

Time spent waiting for locks or resources.

Explain plan

A detailed breakdown of how the DBMS plans to execute the query.

Main lesson · 4

Written queries vs. SQL processing

The database doesn’t execute your human-readable SQL directly.

  1. Parsing and syntax checking: the DBMS verifies the SQL is valid; otherwise it returns an error.
  2. Query optimization: evaluates multiple ways to get the data, checking indexes, table statistics and data distribution.
  3. Execution plan: the most efficient path (e.g., “use the index on last_name, then filter by city”).
  4. Execution: the engine runs the plan and returns results.

Main lesson · 5A

Modern best practices

Write queries the optimizer can work with.

Use EXPLAIN ANALYZE

In PostgreSQL and MySQL, prefixing a query with EXPLAIN ANALYZE runs it and shows the actual execution plan, including where time is spent.

Avoid SELECT *

Only retrieve the columns you need. It reduces I/O and network traffic.

CTEs over subqueries

WITH clauses make complex queries readable and often help the optimizer plan better.

Main lesson · 5B

Beware of non-“sargable” queries

Avoid using functions on indexed columns in the WHERE clause.

Bad vs. good (SQL)
-- Bad: function on an indexed column
-- (forces a full scan)
WHERE YEAR(order_date) = 2024

-- Good: lets the database use the index
WHERE order_date >= '2024-01-01'
  AND order_date < '2025-01-01'

Why

Wrapping the indexed column in a function forces a full scan. Comparing the raw column to a range lets the database use the index.

Analogy

The restaurant kitchen

  • The query: a customer’s complex order (a 5-course meal with substitutions).
  • The DBMS: the Head Chef.
  • The optimizer: decides whether to cook the steak first or boil the pasta, and whether the ingredients are prepped (indexed).
  • The execution plan: the step-by-step recipe.
  • Caching: pre-chopped vegetables (mise en place). The same order next time is much faster.

Real-world use case

E-commerce on Black Friday

The products table has 5 million rows and page loads are slow.

  1. EXPLAIN ANALYZE on the product search shows a full table scan (all 5 million rows).
  2. They add an index on category_id.
  3. They implement caching with Redis for the most popular product pages.

Result: query time drops from 4.5 seconds to 15 milliseconds.

FAQs

Common questions

Common optimization techniques?

Index frequently searched columns, normalize (or strategically denormalize) tables, partition large tables, use caching, and rewrite queries to be more efficient (e.g., avoid SELECT *).

Measuring performance?

Execution time, CPU and memory usage, I/O operations, and the execution plan (EXPLAIN or EXPLAIN ANALYZE).

An index on every column?

No. Indexes speed up reads but slow down writes and use disk space. Index columns frequently used in WHERE, JOIN or ORDER BY.

Subquery vs. view?

A subquery is a temporary query inside another query. A view is a named, persistent (but virtual) table in the schema, reusable by many queries or applications.

Hands-on exercise

Optimize a slow query

A customers table has 2 million rows, and a query using LOWER(email) takes 5 seconds. LOWER() on the column prevents the index from being used, so every row is scanned.

Task 1

Rewrite the query to be sargable (index-friendly), assuming data is stored in lowercase. Also replace SELECT * with specific columns to reduce I/O.
Slow query (SQL)
-- Slow: LOWER() prevents index use
SELECT * FROM customers
WHERE LOWER(email) = 'user@example.com';

Task 2

If you must search case-insensitively, create a function-based index.
Fix 1: sargable query (SQL)
-- Optimized: sargable, specific columns
SELECT customer_id, first_name, last_name
FROM customers
WHERE email = 'user@example.com';
Fix 2: function-based index (SQL)
-- Function-based index (modern solution)
CREATE INDEX idx_customer_email_lower
    ON customers (LOWER(email));

-- Now this query can use the new index
SELECT * FROM customers
WHERE LOWER(email) = 'user@example.com';

Key quotes

Key definitions to remember

SQL optimization

Improving performance by reducing the CPU, memory and I/O a query needs.

Execution plan

The steps the DBMS will take to run a query (indexes used, join order).

Full table scan

Reading every row because no index was used. Shows up as high I/O.

Sargable query

A query written so the database can use an index.

Recap

Measure, then optimize

SQL optimization combines strategic indexing, intelligent database design (normalization vs. denormalization) and an understanding of how the query optimizer builds execution plans.

Analyze I/O and CPU metrics, use EXPLAIN, and let modern tuning tools help you remove bottlenecks and scale efficiently.
