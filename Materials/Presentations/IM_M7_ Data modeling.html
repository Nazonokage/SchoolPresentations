Main lesson · 1

What is data modeling?

Data modeling is the process of creating a conceptual representation of data, typically a data model. The model defines the structure of a database: how data is organized, stored and interrelated.

Entities

The things we store data about.

Attributes

Their characteristics.

Relationships

The links between entities.

Data modeling helps teams understand data requirements, constraints and business rules before implementation begins.

Main lesson · 2A to 2C

What each level adds

Conceptual

A high-level, abstract view. It identifies the real-world entities the organization cares about (Customer, Order, Product) and how they relate. Benefit: a communication tool that aligns stakeholders without technical jargon.

Logical

Adds structure and precision while staying independent of any database technology. Entities get attributes, data types, primary keys and foreign keys. Normalization is applied to reduce redundancy and improve data quality.

Physical

The final blueprint, tailored to a specific DBMS. It defines table names, column data types, indexes, constraints and storage parameters. Partitioning, clustering and denormalization are decided here to optimize performance (e.g., Snowflake, PostgreSQL, Databricks).

Main lesson · 3

Best practices in data modeling

Established practices keep a model robust, scalable and easy to maintain.

  1. Understand the business requirements: know how the data will be used and what problems it solves.
  2. Use a consistent naming convention: for entities, attributes and relationships.
  3. Avoid data redundancy: eliminate it to keep the model simple and consistent.
  1. Enforce data integrity: use constraints and rules so data stays accurate over time.
  2. Model for usability: design for the end user, whether an analyst, a stakeholder or a machine learning pipeline.

Main lesson · 4A

Relational and NoSQL models

The traditional choice was Relational or NoSQL. Today the industry recognizes that no single database fits every workload, which led to Polyglot Persistence: using multiple database technologies within a single architecture, each chosen for its strengths.

Relational model (SQL)

Data in tables with rows and columns, linked by keys. PostgreSQL and MySQL provide strong consistency, ACID transactions and powerful SQL querying. The dependable core for transactional systems.

NoSQL and document model

Flexible schemas. Document databases (e.g., MongoDB) store JSON-like documents, allowing rapid iteration and horizontal scaling. Ideal for semi-structured data, social feeds and real-time applications.

Main lesson · 4B

Modern update: the blurring of lines

The boundaries between SQL and NoSQL have weakened.

PostgreSQL

Supports JSONB columns for semi-structured data and pgvector for AI embeddings.

MongoDB

Now supports ACID transactions and aggregation pipelines.

The real challenge in 2026 is knowing where to draw the line for each workload.

Main lesson · 4C

Vector databases and AI integration

The most significant modern shift is the rise of vector databases (or vector search built into existing databases). They store high-dimensional vectors (embeddings) that represent the semantic meaning of text, images or audio.

They are the backbone of RAG (Retrieval-Augmented Generation) architectures for Large Language Models, letting AI applications run semantic similarity searches.

Pro tip: By 2026, vector search is no longer a niche add-on. Mainstream relational and document databases increasingly offer it as a core capability, simplifying AI application architecture.

Main lesson · 5

Object-oriented vs. relational

Object-oriented (historical)

Designed to represent data as objects, like OOP languages; useful for complex data sets and multimedia. Pure OODBMS are niche today.

Modern alternatives

Object data is typically mapped to relational tables with an ORM (Object-Relational Mapper). Or use a document database to store nested, object-like data without a rigid table schema.

Analogy

The building blueprint

Conceptual model

A napkin sketch of the house: “We need a kitchen, a living room and two bedrooms, and the kitchen connects to the living room.” It is about communication.

Logical model

The detailed blueprint with exact dimensions, door placements and wiring rules. Technology-agnostic: the same blueprint could be built with wood or brick.

Physical model

The construction plan for a specific location: the exact brand of materials, the foundation depth for the local soil, the HVAC system. Tailored to the environment.

Real-world use case

An e-commerce platform’s polyglot architecture

A modern e-commerce giant doesn’t use just one database.

  1. Relational (PostgreSQL): user accounts, billing and financial transactions, where strict consistency is non-negotiable.
  2. Document (MongoDB): the product catalog. Product A has sizes and colors; Product B is a book with an ISBN.
  1. Vector (pgvector/Pinecone): the AI recommendation engine, finding semantically similar products.
  2. Graph (Neo4j): the “Friends who bought this” feature, querying highly connected relationships.

FAQs

Common questions

Object-oriented or relational?

It depends on the project’s needs. Relational is the industry standard for structured data and enterprise applications thanks to its maturity and consistency. Today most “object-oriented” data is mapped to relational tables via ORMs or stored in document databases.

Multiple data models in one project?

Absolutely. That is the core of polyglot persistence. Microservices architectures often assign a database type to each service.

Conceptual vs. logical?

Conceptual defines high-level entities and relationships (“A Customer places an Order”). Logical adds attributes, primary keys and foreign keys but stays independent of any database software.

Why are vector databases important?

They store data as mathematical embeddings, so computers can search by semantic meaning rather than exact keywords. Essential for AI apps such as chatbots searching a company knowledge base.

Recap

From concept to polyglot architecture

Data modeling moves from conceptual business alignment to logical structuring and finally physical implementation.

The relational model remains the backbone for transactional data, while modern architecture embraces polyglot persistence, integrating NoSQL, document and vector databases for diverse workloads, especially AI and real-time analytics.
