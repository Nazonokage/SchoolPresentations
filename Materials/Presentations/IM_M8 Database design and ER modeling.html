Main lesson · 1

Database design: the blueprint

Database design is the process of creating a structured plan for how data will be stored, organized and accessed. It identifies the data to store, the relationships between the data, and a logical and physical structure.

  1. Gather and analyze requirements: what data the business needs and how it flows.
  2. Create a conceptual model: high-level entities, attributes and relationships (the ER model).
  3. Translate to a logical model: the schema, rules, constraints and keys.
  4. Create a physical model: how data is stored, optimized for the DBMS (indexes, partitioning).
  5. Implement and populate: build the database and load data.

Main lesson · 2

Why is database design important?

Performance and scalability

Proper design makes data easier to retrieve and update efficiently, even as the dataset grows.

Data integrity and consistency

Rules and constraints keep the data accurate.

Security

Control access to sensitive information through well-defined structures.

Maintainability

A logical, well-documented design is easier to maintain, update and expand.

Modern update

Schema-as-Code and CI/CD

Database design is no longer a one-time, manual event. Teams use Schema-as-Code tools (like Atlas or Bytebase) to define database structure in code files.

These tools integrate with CI/CD pipelines, automatically generating migration scripts, detecting schema drift, and keeping database changes version-controlled and tested like application code.

Main lesson · 3

The Entity-Relationship (ER) model

The ER model is a conceptual representation of the data and its relationships, and the most common way to model a database before implementation.

ComponentDescriptionExample
EntityAn object or concept about which data is stored.Student, Course, Product
AttributeA characteristic or property of an entity.Student_ID, Name, Email
RelationshipA connection between entities.A Student enrolls in a Course
CardinalityHow many instances of one entity can relate to another.One-to-One, One-to-Many, Many-to-Many
Primary Key (PK)Uniquely identifies an instance of an entity.Student_ID
Foreign Key (FK)Refers to the primary key of another entity.Course_ID in Enrollment

Main lesson · 4

Relationships and cardinality

Cardinality specifies the maximum number of relationship instances an entity can participate in.

One-to-One (1:1)

One entity relates to exactly one instance of another. A person has one driver’s license.

One-to-Many (1:N)

One entity relates to multiple instances of another. A department has many employees.

Many-to-Many (M:N)

Multiple instances relate to multiple instances. A student enrolls in many courses; a course has many students.

In relational databases, M:N relationships are resolved using a junction (associative) table.

Main lesson · 5

Visualizing the model: ERDs

Chen notation

Traditional. Uses shapes: rectangles for entities, ellipses for attributes, diamonds for relationships.

Crow’s Foot notation

Modern software engineering predominantly uses it: more compact and readable for complex schemas. Attributes sit inside the entity rectangle and line-end symbols show cardinality.

Pro tip: Tools like dbdiagram.io, Lucidchart and Miro support Crow’s Foot notation. You can even define schemas in DBML (Database Markup Language) and generate the diagram automatically.

Modern evolution · A

AI-assisted data modeling

AI is now embedded in the design process. Modern tools can:

Infer schemas from raw data

Point an AI at a CSV or JSON file and it suggests a normalized table structure, relationships and data types.

Generate schemas from natural language

Describe the domain in plain English (“a blog platform with users, posts and tags”) and tools like Cursor with an MCP Server generate the schema and migration files.

Automate documentation and impact analysis

AI writes column descriptions and warns if a schema change will break downstream reports or dashboards.

Important caveat: AI excels at the mechanical aspects (naming conventions, boilerplate tables) but lacks business context. Choosing integer or decimal for price, or handling multi-tenancy, still needs human judgment.

Modern evolution · B

Semantic modeling and vector embeddings

Generative AI and LLMs introduced a new data type: vector embeddings. Databases like Azure Cosmos DB, SQL Server 2025 and PostgreSQL (via pgvector) store high-dimensional vectors alongside relational or document data.

This creates semantic data models: schemas that capture not just explicit relationships (foreign keys) but the conceptual meaning of data. A product table with an embedding column can answer “find products similar to this image” without a separate vector database.

Analogy

The architectural blueprint

Conceptual ERD

The napkin sketch. It shows the “rooms” (entities like Customer and Order) and how they connect. About business communication.

Logical schema

The detailed blueprint with dimensions, doors and wiring rules (attributes, primary keys, foreign keys). Technology-agnostic.

Physical schema

The construction plan: the exact brand of concrete and placement of load-bearing walls (indexes, data types, partitions). Tied to a specific DBMS.

Real-world use case

A modern library system

Design an ERD for a library.

  • Entities: Book, Author, Borrower.
  • Book: ISBN (PK), Title, Publication_Date.
  • Author: Author_ID (PK), Name, Date_of_Birth.
  • Borrower: Borrower_ID (PK), Name, Address, Phone_Number.
  • Book to Author: many-to-many.
  • Book to Borrower: many-to-many (borrowed by many over time).
  • Resolution: junction tables Book_Author and Loan (with a Due_Date attribute).
  • AI-assisted tools can generate this structure from a natural-language prompt.

Hands-on exercise

Design a streaming service ERD

Scenario

A video streaming platform like Netflix. Users have User_ID (PK), Email and Subscription_Tier. Movies have Movie_ID (PK), Title and Release_Year. Users watch many movies and movies are watched by many users; track Watch_Date and Completion_Percentage.
  1. Identify the entities.
  2. Identify the primary keys.
  3. Determine the cardinality.
  4. Write the DBML (paste it into dbdiagram.io to see the ERD).
DBML schema
Table Users {
  user_id integer [primary key]
  email varchar [unique]
  subscription_tier varchar
}

Table Movies {
  movie_id integer [primary key]
  title varchar
  release_year integer
}

Table ViewingHistory {
  user_id integer [ref: > Users.user_id] // FK
  movie_id integer [ref: > Movies.movie_id] // FK
  watch_date timestamp
  completion_percentage integer

  Note: 'Junction table for the M:N link'
}

FAQs

Common questions

Entity vs. table?

An entity is a conceptual real-world object (“Student”). A table is its physical implementation in a relational database. One entity typically maps to one table, though complex designs may spread it across several.

Why a junction table for M:N?

Relational databases cannot directly link many rows to many rows. A junction table holds foreign keys to both entities, breaking M:N into two 1:N relationships.

Chen vs. Crow’s Foot?

Chen uses separate shapes (diamonds, ovals). Crow’s Foot lists attributes inside the entity rectangle and uses line-end symbols for cardinality; it is preferred for readability.

Always draw an ERD first?

You can create tables directly in SQL, but drawing an ERD (or defining schema as code) is highly recommended. It prevents costly rework.
