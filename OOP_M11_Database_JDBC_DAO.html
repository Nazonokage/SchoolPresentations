Section A.2 · The DAO Pattern

Why Separate Data Access at All?

The Data Access Object pattern isolates raw database interaction logic from your core business logic.

Core Benefits

What the DAO Pattern Buys You

🔗 Decoupling

Changes to SQL queries or table schemas don't break the application's business logic — the DAO absorbs the change.

🧹 Maintainability

SQL queries live in one centralized place — inside DAO classes — instead of scattered across the codebase.

🛡️ Security

Centralizing data access makes it far easier to enforce strict parameter sanitization via PreparedStatement, every single time.

🔁 Familiar Shape

Notice the pattern: an interface (UserDAO) defines what, a concrete class (UserDAOImpl) defines how — exactly the interface habit from Modules 9–10.

🔍 Reading This Code

  • ? placeholders mark where values go — stmt.setString(1, ...) fills the 1st placeholder (parameter indices are 1-based, not 0-based!)

SQL Injection: Seeing the Danger

Never concatenate user input directly into a raw SQL string. Let's see exactly why.

What just happened: the attacker's input didn't just fill in a name — it rewrote the query's logic. '1'='1' is always true, so this query could return every user in the table, or bypass a login check entirely.

The Fix

PreparedStatement Shuts the Door

✅ Secure — Parameterized

secure.java

Why This Works

A PreparedStatement sends the query's structure to the database first, fully locked in. Only afterward does it send the values to slot into each ?. There's no way for a value to "break out" and rewrite the query — it's like a fill-in-the-blank form, not an open text field someone can scribble new instructions onto.

Making It Stick

Real-Life Analogies

DAO Pattern restaurant kitchen

The waiter (business logic) never cooks — they just place an order with the kitchen (DAO). The kitchen's recipes can change completely without the waiter's script changing at all.

PreparedStatement fill-in-the-blank form

The form's structure is fixed and printed. You can only write inside the blanks — you can't scribble new instructions into the margins that change what the form does.

try-with-resources automatic door closer

You never have to remember to shut it behind you — it closes itself the moment you leave the room, even if you left in a hurry (an exception).

ResultSet.next() flipping index cards

One card at a time, front to back — next() flips to the next card and tells you whether there was one left to flip to.

Section E · Wrap-Up

Frequently Asked Questions

What is the DAO pattern, and why use it?

It provides a unified interface between application logic and persistence storage. Encapsulating SQL inside DAO classes means schema changes don't ripple into business logic.

executeQuery() vs. executeUpdate()?

executeQuery() is for SELECT statements, returning a ResultSet. executeUpdate() is for INSERT/UPDATE/DELETE, returning an int row count.

How does try-with-resources prevent leaks?

It automatically closes any AutoCloseable resource — Connection, PreparedStatement, ResultSet — at the end of the block, even if an exception occurs.

What exactly is a ResultSet?

A cursor over the rows a query returned. Call rs.next() to advance one row at a time, then rs.getInt("col") / rs.getString("col") to read that row's values.

Before the Skill Check

Recap

Connecting & Structuring

  • JDBC (Java) and PDO (PHP) both open a connection to a relational database through a driver
  • try-with-resources auto-closes Connection, PreparedStatement, and ResultSet
  • The DAO pattern: a model (User), an interface (UserDAO), and an implementation (UserDAOImpl)

Reading, Writing & Staying Safe

  • executeQuery() → SELECT → ResultSet; executeUpdate() → INSERT/UPDATE/DELETE → row count
  • Parameter indices in PreparedStatement are 1-based, not 0-based
  • Never concatenate user input into SQL — PreparedStatement / PDO's execute([...]) keep values as pure data, always
