Section A · Lesson Preview

The Four Building Blocks

Scalable, maintainable Java applications rest on structured modularization and deliberate memory management. Everything in this deck builds on these four ideas.

Methods

Self-contained blocks of code designed to perform one specific operation. They promote reuse — write the logic once, call it wherever it's needed.

Arrays

Linear data structures storing a fixed-size, sequential collection of elements of the same type — indexed slots sitting in contiguous memory.

Classes & Objects

Classes are the blueprints; objects are the running instances built from them. Every OOP mechanic in this deck exists to make that blueprint safer to reuse.

Encapsulation

The practice of bundling data (fields) and code (methods) together, while restricting direct access to an object's internals from the outside world.

Section B.1 · Method Structure

Anatomy of a Method Signature

Every Java method signature declares five things, in order: who can call it, whether it needs an object, what it hands back, its name, and what it needs from you.

[Access Modifier] [Static/Non-Static] [Return Type] methodName(ParameterType param1, ...) { // Method body logic return value; // Required if Return Type isn't 'void' }
Access Modifier
Who's allowed to call this: public, private, protected, or default.
Static / Non-Static
static belongs to the class itself; non-static needs an object instance to run.
Return Type
The data type sent back to the caller — or void if nothing is returned.
Method Name
The identifier used to call it — conventionally a verb, like calculateTotal.
Parameters
The inputs the method needs to do its job, each with its own type.

Rule 2 of 3 · Reusability

Method Overloading — Same Name, Different Signatures

Multiple methods can share the exact same name as long as their parameter lists differ. Java figures out which version to run at compile time, based on the arguments you pass.

What's Allowed to Differ

  • Number of parameters — one argument vs. three
  • Order of parameter types — (String, int) vs. (int, String)
  • Type of parameters — int vs. double vs. String

What Does Not Count

  • Return type alone — two methods with identical parameters but different return types will not compile
  • Parameter names — the compiler only cares about types and order, not what you call them
  • Access modifier alone — public vs private doesn't create a valid overload

⚠ Watch Out: Overload Ambiguity

Calling calculateTotal(25.00, 4) matches (double, int) exactly — no ambiguity. But if you also declare an (int, int) overload, and call it with two whole numbers like calculateTotal(25, 4), Java prefers the exact match over widening an int to a double.

Takeaway: when in doubt, be explicit about literal types (25.0 vs 25) so the overload you expect is the one that actually runs.

Section B.3 · Object-Oriented Programming

Encapsulation: Locking the Blueprint

Encapsulation hides a class's attributes behind private, then exposes only the interaction you intend through public getters and setters.

Why Bother Hiding Fields?

  • Data integrity — a setter can reject bad input (like an email with no @) before it ever gets stored
  • Flexibility — you can change how a field is stored internally later, without breaking code that calls the getter
  • Controlled access — read-only fields simply skip the setter entirely

Constructors

Default, Parametric & Constructor Chaining

A constructor is a special routine, matching the class name, with no return type, that runs automatically the moment new creates an object.

Three Flavors

  • Default constructor — takes no arguments, often fills in sensible fallback values
  • Parametric constructor — accepts arguments to set fields immediately on creation
  • Constructor overloading — multiple constructors, same class, differing parameter lists (the same rule as method overloading, applied to constructors)

Constructor Chaining with this(...)

chaining.java

this(...) calls another constructor in the same class, so initialization logic lives in exactly one place. It must be the very first statement — Java only allows one such call, and only at the top.

The super Keyword

Reaching Back to the Parent Class

Two Uses of super

  • super(args) — calls the parent class's constructor. Must be the first line of the subclass constructor.
  • super.methodName() — calls the parent's version of a method you've overridden, from inside your override.

Both let a subclass reuse the parent's logic instead of copy-pasting it.

Real-Life Analogies

Method vending machine

Press the same button, get the same product every time. You don't need to know the internal wiring — just the input (button) and the output (snack).

Array egg carton

A fixed number of slots, each holding exactly one item, numbered by position. You can't add a 13th egg to a 12-slot carton without a new carton.

Class / Object blueprint / house

An architect's blueprint defines the design once. Every house built from it is a separate object — same layout, different furniture inside.

Encapsulation medicine capsule

The active ingredients are sealed inside. You interact through the intended dosage, not by cracking the capsule open yourself.

Section E · Wrap-Up

Frequently Asked Questions

Overloading vs. Overriding?

Overloading: same class, different parameter signatures, resolved at compile time. Overriding: superclass/subclass, identical signature, resolved at runtime.

Why use constructors?

They run automatically on new, guaranteeing an object starts in a valid, fully initialized state with every necessary field assigned.

How does this work?

It refers to the current instance — used in constructors and setters to distinguish a field from a parameter sharing the same name, e.g. this.name = name.

Can an array resize itself?

No — Java arrays are fixed-size once created. For collections that grow and shrink, reach for ArrayList or another Java Collections Framework structure.

Before the Skill Check

Recap

Methods & Arrays

  • Method signatures: access, static/non-static, return type, name, parameters
  • Java is always pass-by-value — even "reference passing" is really a copied address
  • Overloading = same name, different parameter list, resolved at compile time
  • Arrays are fixed-size, zero-indexed, contiguous — watch your bounds

Encapsulation & Inheritance

  • Encapsulation: private fields + public getters/setters for controlled, validated access
  • Constructors chain with this(...); subclasses chain to parents with super(...)
  • Inheritance builds an IS-A relationship via extends
  • Overriding = identical signature, resolved at runtime, customizes inherited behavior
