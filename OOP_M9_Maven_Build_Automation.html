Brewing Basics

What Is Apache Maven?

Apache Maven is an industry-standard build automation tool for Java projects. It standardizes project layout, handles external library dependencies automatically, and provides a uniform build lifecycle to compile, test, and package applications.

The Standard Maven Directory Structure

Maven relies on Convention over Configuration. By following a predictable directory structure, Maven understands where source code, resources, and tests reside — no complex scripts required.

my-app/ ├── pom.xml // Project Object Model (config) └── src/ ├── main/ │ ├── java/ // Application source code (.java) │ └── resources/ // Config files, properties, assets └── test/ └── java/ // Unit test code (e.g. JUnit)

🔍 Why This Matters

  • pom.xml — always lives at the project root, the recipe card Maven reads first
  • src/main/java — your actual application code, organized by package folders
  • src/main/resources — non-code files bundled into the final JAR (properties, configs)
  • src/test/java — test code, completely separate from production code — it never ships in the final JAR

💡 Key Takeaway

Every Maven project — yours, your teammate's, an open-source library — looks the same at a glance. That predictability is the entire point.

Section B.1 · The pom.xml File

Anatomy of Project Coordinates

Every Maven project is uniquely identified by three coordinates — together they form its "address" in the Maven world.

<groupId>com.example.app</groupId> <artifactId>app-runner</artifactId> <version>1.0.0</version> <packaging>jar</packaging>
groupId
Organization or namespace — conventionally a reversed domain name.
artifactId
The project's own name — becomes the base of the final JAR filename.
version
The release number — bump it every time you ship a new build.
packaging
The output type — jar, war, or pom for parent projects.

Together these produce the final artifact name: app-runner-1.0.0.jar — exactly what you'll see appear in target/ after a build.

The Full Maven Build Lifecycle

The lesson's commands (clean, compile, package) are just three stops on a longer, standardized pipeline — and running any later phase automatically runs every phase before it.

validate / compile

Checks the project structure is correct, then turns .java files into .class bytecode.

test / package

Runs unit tests from src/test/java, then bundles everything into a .jar (or .war).

verify / install

Runs extra checks, then copies the artifact into your local ~/.m2 repository for other local projects to use.

deploy

Copies the final artifact to a shared remote repository so teammates (or the world) can use it too.

Common Errors & How to Read Them

"package org.apache.commons.lang3 does not exist"

The dependency isn't declared in pom.xml (or hasn't downloaded yet). Add the <dependency> block and re-run mvn compile.

"no main manifest attribute, in ...jar"

The JAR built successfully, but <mainClass> was never configured in the maven-jar-plugin section.

"invalid target release: 17"

pom.xml targets Java 17, but the installed JDK is older. Either upgrade the JDK or lower maven.compiler.target.

Stale or "phantom" build errors

Old compiled classes lingering in target/ can cause confusing errors. Run mvn clean first, then rebuild.

Real-Life Analogies

pom.xml recipe card

Lists every ingredient (dependency), the recipe name (coordinates), and how the final dish should be packaged.

Maven Central wholesale supplier

The regional supplier who has virtually every ingredient in stock, ready to deliver the moment you order it.

Local cache (~/.m2) shop pantry

Once you've ordered flour, you don't re-order it for the next batch — it's already sitting in your own pantry.

Build lifecycle the roasting line

Raw beans go in one end (validate, compile), get roasted and tested along the way, and come out the other end sealed and labeled (package) — ready to ship (deploy).

Barista FAQ

Wrap-Up & FAQs

What does pom.xml stand for?

Project Object Model. It holds the configuration Maven uses to build the project — dependencies, plugins, source directories, and version metadata.

How does Maven fetch external libraries?

A <dependency> tag in pom.xml triggers Maven to download the .jar from the central Maven Repository and cache it locally at ~/.m2/repository.

mvn compile vs. mvn package — what's the difference?

compile turns .java into .class bytecode. package does that, runs tests, and wraps everything into a final .jar (or .war).

Why use Maven instead of plain javac?

Manual compilation means tracking every library path and compilation order by hand. Maven automates all of it with standardized, repeatable commands.

Before the Skill Check

Recap

  • pom.xml is the recipe card — coordinates, dependencies, and build plugins all live here.
  • Maven's standard directory structure (src/main/java, src/test/java) means every project looks familiar.
  • Dependencies resolve through a chain: local cache first, Maven Central if missing — then cached for next time.
  • The build lifecycle runs in order — validate, compile, test, package, verify, install, deploy — and later phases always run the earlier ones first.
  • mvn clean package then java -jar target/your-app.jar is the everyday two-step build-and-run habit.
  • Most build errors trace back to a missing dependency, a missing mainClass, or a Java version mismatch.
