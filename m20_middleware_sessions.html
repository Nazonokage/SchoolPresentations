🔗 The Missing Piece

Our routes work — but how do we check if a user is logged in before they reach the dashboard? How does the server remember who they are across requests? That's middleware and sessions.

💡 The Problem with Stateless HTTP

By default, HTTP is stateless — the server forgets you the moment each request ends. A user logs in on Page 1, but by Page 2 the server has no memory of them. Sessions solve this. Middleware is how we intercept requests to check those sessions before reaching the route.

Core Concept

What Is Middleware?

Middleware is a function that sits between an incoming HTTP request and the final route handler. It has access to req, res, and a special next() function that passes control to the next middleware in the stack.

Origin
Client
→request
Middleware
MW 1
→next()
Middleware
MW 2
→next()
Destination
Route Handler
→response
Reply
Client

req — Request Object

Middleware can read and modify the incoming request — add properties, check headers, read the body.

res — Response Object

Middleware can end the cycle early — redirect unauthorized users, return an error, or set response headers.

next() — Pass Control

Calling next() hands control to the next function in the stack. Without it, the request hangs forever — nothing responds.

⚠️ Order matters: Middleware runs sequentially in the order you declare it with app.use(). Middleware declared first runs first — always define body parsers and session middleware before your routes.
Middleware Types

3 Types of Middleware

🔵 Built-in Middleware
const express = require('express');
const app     = express();

// Parse JSON bodies (API requests)
app.use(express.json());

// Parse form submissions
app.use(express.urlencoded({
  extended: true
}));
🟢 Custom Middleware
// 3 args: req, res, next
const logger = (req, res, next) => {
  console.log(
    `${req.method} ${req.url}`
  );
  next(); // must call next()!
};

app.use(logger); // apply globally
🔴 Error-Handling Middleware
// 4 args: err, req, res, next
const errorHandler =
  (err, req, res, next) => {
    console.error(err.stack);
    res.status(500).json({
      error: 'Internal Server Error'
    });
  };

app.use(errorHandler);

Built-in — What They Do

express.json() parses JSON bodies. express.urlencoded() parses HTML form data. Both populate req.body.

Custom — Signature

Always takes (req, res, next). Do your work, then always call next() unless you're ending the response yourself.

Error Handler — 4 Args

The 4-argument signature (err, req, res, next) is how Express identifies error-handling middleware. Must be declared last, after all routes.

Middleware Order

Execution Order & Scope

JS — Order & Scope
const express = require('express');
const app     = express();

// GLOBAL — runs on EVERY request
const middleware1 = (req, res, next) => {
  console.log('MW1: runs on every request');
  next();
};

const middleware2 = (req, res, next) => {
  console.log('MW2: also runs on every request');
  next();
};

// ROUTE-LEVEL — only on this specific route
const middleware3 = (req, res, next) => {
  console.log('MW3: only runs for GET /route');
  next();
};

app.use(middleware1);  // global
app.use(middleware2);  // global

app.get('/route', middleware3, (req, res) => {
  res.send('Route reached!');
});

// Error handler — always last
app.use((err, req, res, next) => {
  res.status(500).json({ error: err.message });
});

📋 Execution for GET /route

1

middleware1 runs (global)

Logs the request. Calls next() to continue.

2

middleware2 runs (global)

Also logs. Calls next() to continue.

3

middleware3 runs (route-level)

Only runs because it's attached directly to this route. Calls next().

4

Route handler runs

Final destination — sends the response. No next() needed here.

Global vs Route-level: app.use(fn) applies to every request. Passing middleware as a route argument app.get('/path', fn, handler) scopes it to that route only.
Cookie Sessions

Sessions — Making HTTP Stateful

HTTP is stateless — every request is independent. Sessions solve this by letting the server remember who a user is across multiple requests.

🌐
Browser (Client)
Stores only the
Session ID Cookie
(a small ticket number)
→ Request + Cookie ID →
← Response + Set-Cookie ←
🖥️
Server (Express)
Stores actual
Session Data
(username, cart, preferences)

1. First Visit

Server creates a unique Session ID, stores it in a cookie sent to the browser. User data is saved server-side under that ID.

2. Subsequent Requests

Browser automatically includes the cookie. Server reads the Session ID, looks up the data, and makes it available via req.session.

3. Logout

Call req.session.destroy(). The server deletes the session data. The cookie on the browser becomes useless — effectively logging the user out.

Cookie vs Session: The cookie holds only the Session ID (like a coat check ticket). The session is the actual data stored securely on the server (like your coat in the back room).
express-session

Configuring Cookie Sessions

JS — Session Setup
// Step 1: Install
// npm install express-session

const express = require('express');
const session = require('express-session');
const app     = express();

// Step 2: Configure the session middleware
app.use(session({
  secret           : 'YourSecretKey',
  resave           : false,
  saveUninitialized: true
}));

// Step 3: Store data in the session
app.get('/set', (req, res) => {
  req.session.username = 'Radoslava';
  res.send('Session set!');
});

// Step 4: Read session data
app.get('/get', (req, res) => {
  const name = req.session.username;
  res.send(`Hello, ${name}!`);
});

// Step 5: Destroy the session (logout)
app.get('/logout', (req, res) => {
  req.session.destroy((err) => {
    if (err) console.error(err);
    res.redirect('/login');
  });
});

app.listen(3000);

⚙️ Configuration Options

!

secret — Sign the Session ID

A complex, unguessable string used to sign the session cookie. In production, store it in a .env file — never hardcode it.

2

resave: false

Prevents the session from being saved back to the store on every request if nothing changed. Reduces unnecessary writes — recommended setting.

3

saveUninitialized: true

Saves new but unmodified sessions to the store. Useful for apps that need to track visitors before they log in.

4

req.session.destroy()

Deletes the session from the server store. The callback fires once destroyed — redirect the user to the login page inside it.

🔒 Secure flag: Set cookie: {"{"} secure: true {"}"} in production to ensure the session cookie is only sent over HTTPS — never plain HTTP.

Guided Drill — Phase 2

Login System: server.js

JS — server.js (complete)
const express    = require('express');
const session    = require('express-session');
const bodyParser = require('body-parser');
const app        = express();
const port       = 3000;

// Middleware setup (ORDER MATTERS)
app.use(bodyParser.urlencoded({ extended: true }));
app.use(session({
  secret           : 'YourSecretKey',
  resave           : false,
  saveUninitialized: true
}));
app.set('view engine', 'ejs');

// GET /login — show the login form
app.get('/login', (req, res) => {
  res.render('login');
});

// POST /login — handle form submission
app.post('/login', (req, res) => {
  const { username } = req.body;
  req.session.username = username; // save to session
  res.redirect('/dashboard');
});

// GET /dashboard — protected route
app.get('/dashboard', (req, res) => {
  if (req.session.username) {
    res.render('dashboard', {
      username: req.session.username
    });
  } else {
    res.redirect('/login'); // not logged in
  }
});

// GET /logout — destroy session
app.get('/logout', (req, res) => {
  req.session.destroy((err) => {
    if (err) console.log(err);
    res.redirect('/login');
  });
});

app.listen(port, () =>
  console.log(`Server on port ${port}`)
);

3

Checks req.session.username. If present → render dashboard with name. If absent → redirect to login.

4

Real-World Analogies

Middleware & Sessions in the Real World

✈️ Airport Security (Middleware)

Getting to the plane (Route Handler) requires passing multiple checkpoints first:

  • ID Check (auth middleware) — validates your identity
  • Baggage Scanner (body parser) — inspects the request payload
  • Boarding Pass Stamp (next()) — grants passage to the next stage
  • Denied entry — middleware ends the cycle with an error or redirect

🧥 The Coat Check (Sessions)

HTTP is like a restaurant that forgets you instantly. Sessions are the coat check:

  • Host gives you a numbered ticket (Session ID Cookie)
  • Your coat (user data) is in the back room (server session store)
  • Every visit, show your ticket → host finds your coat
  • At logout, you return the ticket and they clear your locker (session.destroy())

Real-World Use Cases

🔐 Auth Guards

Check if user is logged in before allowing access to protected pages.

🛒 Shopping Carts

Items added to cart persist across page navigations without re-login.

📊 Analytics Logging

Custom logger middleware tracks every page visit for usage insights.

🚦 Rate Limiting

Middleware restricts how many API requests a user can make per minute.

Lesson Wrap-Up

FAQs & Summary

❓ How do I use middleware in Express.js?

Use app.use(fn) to apply middleware globally. Write it with the (req, res, next) signature, do your work, then call next() to pass control to the next function. Built-in options like express.json() work the same way.

❓ What is the difference between a session and a cookie?

A Cookie is stored in the browser — in a session system, it holds only the Session ID. The Session is the actual data (username, cart) stored securely on the server. The cookie is the ticket; the session is the coat in the back room.

❓ Can middleware validate JSON data?

express.json() parses but doesn't validate structure. Use validation libraries like Joi, Yup, or Validator.js — write a middleware that checks req.body and calls either next() (valid) or returns a 400 Bad Request error (invalid).

Answer Key — Part 1

Identification & True/False Answers (Q1–7)

Q1: Bridge between server and application for operations on requests
✅ Middleware
Middleware functions intercept every incoming request, run specific logic (auth, parsing, logging), then call next() to pass control down the pipeline.
Q2: Allows defining different middleware in order
✅ Chain of execution (app.use() / next())
The middleware chain — built with app.use() calls and connected by next() — lets you compose modular functionality in any order you need.
Q3: Cookie only sent over this protocol
✅ HTTPS
Setting cookie: {"{"} secure: true {"}"} in the session config ensures the session cookie is never transmitted over insecure HTTP connections.
Q4: Period of communication for storing user-specific data
✅ Session
A session represents the stateful interaction between a user and the server, persisting data like the username and cart across multiple HTTP requests.
Q5: Middleware runs before the route handler?
✅ A — True
Middleware sits in the pipeline before the route handler. It validates, authenticates, or transforms the request before the handler ever runs.
Q6: Cookie sessions store session data on the client-side?
✅ A — True (in context of learning material)
Strictly, only the Session ID is in the cookie — actual data is server-side. However, in the context of this lesson, the mechanism is described as "session data stored client-side via cookies."
Q7: Session data persists across browser sessions by default?
✅ B — False
By default, session cookies are non-persistent — they are deleted when the browser closes. To persist sessions across restarts, you must configure a persistent cookie with an explicit expiry date.

Q9 — Write from Scratch: requireLogin middleware
✅ Reference solution
JS — Q9 Answer
const requireLogin = (req, res, next) => {
  if (req.session.username) {
    next(); // logged in — proceed
  } else {
    res.redirect('/login'); // not logged in
  }
};

// Apply to protect the dashboard
app.get('/dashboard', requireLogin, (req, res) => {
  res.render('dashboard', {
    username: req.session.username
  });
});
